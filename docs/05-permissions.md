# 05 · 权限规则

> 这一层是**最不可见、也最容易迁错**的部分。前端代码里不存在任何权限声明，
> 所有边界都在服务端；本文件是从"前端敢怎么用"反推出来的。

## 1. 一句话模型

**`space_id` 就是权限单元。** 你在某个 `profiles` 行里出现过，就能读写该空间下的所有行；否则一行都看不到。

```
我的可见范围 = { p.space_id | p ∈ profiles, p.owner_id = me }
```

## 2. 逐表反推

| 表 | 读 | 建 | 改 | 删 | 推断依据 |
|---|---|---|---|---|---|
| profiles | 同组 | 本人 | 本人 | 无 | 前端会一次 `select` 全表（#1），update 只改自己（#3 #4） |
| records | 同组 | 本人 | 本人 | 无 | 互相看进度（产品核心）；update 均带自己 id（#6 #8 #10） |
| todos | 同组 | 本人 | 无 | **同组任意** | 删除只按 id 不校验 owner（#15） |
| tags | 同组 | 本人 | 无 | **同组任意** | 同上（#20） |
| rewards | 同组 | 本人 | **同组任意** | **同组任意** | 兑现的是对方的约定（#25 只按 id）；删除也只按 id（#26） |
| messages | 同组 | 本人 | 无 | 无 | 只有 insert / select |

## 3. 两个必须线上核对的疑点

### Q1：`profiles` 的 select 是否真是"同组可见"

前端 `loadAll()` 一次拉全表再按 `space_id` 过滤（`680-696`）。如果线上策略比推断更严（比如只允许看自己），**两个人互相看不见对方**——但产品在线上正常运行，说明策略确实是同组可见。

推断置信度：**高**。

### Q2：`rewards` 的 update 是否真的放开到整组

兑现动作发生在**别人**的约定行上（`owner_id` 是立约人，点击者可能是兑现人）。若线上限定 `owner_id = auth.uid()`，那"帮对方标记已兑现"应当失败。

推断置信度：**中**。需要用真实账号点一次"已兑现"验证；或按 `999` 第 5 段看策略原文。

## 4. 三个隐含的安全约定

1. **`owner_id` 不可伪造**：服务端注入，客户端传了也会被覆盖/忽略。自建时 API 层必须显式丢弃请求体里的 `owner_id`。
2. **`space_id` 不可绕开**：所有 RLS 都以它为准。任何一张表漏写 `space_id`，就会跨组串数据。
3. **`space_peek` 是设计上的例外面**：它让"还没加入的人"读到空间的成员概要（邀请前确认是不是这一组的设计需要），因此必须配合 `docs/07` 风险 6 的频控与返回内容约束；详细分析仅存私有归档。

## 5. 迁移时的落地检查单

- [ ] 6 张表全部 `enable row level security`
- [ ] 6 张表全部 `grant select/insert/update/delete to authenticated`（漏 GRANT 会报 42501，现象像"策略失效"）
- [ ] `my_space_ids()` 用 `security definer`，否则 profiles 策略递归
- [ ] `owner_id` 默认值 `auth.uid()` + `not null`
- [ ] `space_peek` 显式 `revoke from public` 再按需 `grant execute`
- [ ] 用两个真实账号跑一遍：互看进度 / 勾选小目标 / 互发留言 / 兑现 / 删除对方建的小目标 / 切换多组
