## 附 A · Shim 设计（Phase 2.5 的核心）

目标：`index.html` 一行不改，只替换 SDK。

```js
// web/cloud-shim.js —— 只实现 index.html 真正用到的那部分
window.WorkBuddyCloud = {
  createWorkBuddyCloud({ endpoint, publishableKey }) {
    return {
      database: {
        from(table) { /* 返回链式 builder：select/order/eq/insert/update/delete/rpc */ },
        rpc(name, params) { /* 只转发 space_peek */ }
      },
      auth: {
        sendOtp, verifyOtp, getSession, signOut
      }
    };
  }
};
```

三条硬约束：

1. **返回值必须是 `{ data, error }`**，不能抛异常（前端 `unwrap()` 依赖它）。
2. **写入后 `.select()` 要回读整行**，含服务端注入的 `owner_id`。
3. **`order()` 可链式调用两次**，后者为次级排序。

约 200 行。写完可以用 `scripts/` 下的小测试跑一遍 37 个调用点的等价性。

## 附 B · 运行环境取舍（Phase 2.1 决策依据）

| | Supabase 托管 | 自建 Docker |
|---|---|---|
| 上手成本 | 低（邮箱登录开箱可用） | 高（Postgres+PostgREST+GoTrue 三件套） |
| 国内访问 | 一般（境外节点） | 好（可选国内机房） |
| 手机号登录 | 需接第三方（Twilio 对中国号支持差） | 可直连阿里云/腾讯云短信 |
| 每月成本 | 0（免费层） | 60–100 元 |
| 运维 | 平台负责 | 自己备份/续证书/升级 |
| 与现有接口契合度 | **高**（`from().select().eq()` 同构） | 高（PostgREST 同构） |

> 你们选了"手机号 + 邮箱都保留"，这一点会让 Supabase 的成本明显上升（要么接第三方短信、要么自建验证码服务）。若最终走自建，建议直接一台国内轻量服务器 + Docker Compose，一步到位。
