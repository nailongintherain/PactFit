## 1. 当前账号能否访问同一个生产云数据库

**不能。**

证据：

1. 云服务环境探测返回 `count: 0, applications: []`，明确提示"本会话尚无任何应用"。
2. 全盘不存在 `.workbuddy/applications.yaml`——平台的云数据库工具要求传入
   `applicationId`（`wbapp_` 前缀）并从该文件读取，没有这个文件就没有入口。
3. 平台的云数据库工具在服务端会校验"**该应用归属当前用户**"。PactFit 的应用属于
   创建者账号，不属于当前登录账号，因此即使拿到 applicationId 也会被拒。
4. 前端手里唯一能标识应用的只有 `publishableKey`（`wbpk_` 前缀）。它**不是**
   applicationId，按设计不携带任何权限，且只在精确匹配的 Origin 下有效——它无法
   用来打开数据库会话，也无法换取管理权限。

补充说明（很重要）：WorkBuddy 的云服务**没有"把数据库加为协作成员"这种机制**。
它绑定的是「某个账号 + 某个工作区里的应用清单」，不是像 Supabase 那样的组织成员模型。
所以"拿到项目的编辑权限"不可能顺延出"能查它的数据库"。

## 2. 是否有跨全部 `space_id` 的只读 SQL 权限

**没有。** 有两道独立的门，任何一道都过不去：

| 门 | 现状 |
|---|---|
| 身份门 | 当前账号没有任何应用绑定（§1），无法向数据库发起任何 SQL |
| 角色门 | 即便有身份，SQL 执行的角色由模式推导：`read` 只读、`migrate` 管理员。**只有 `migrate` 会绕过 RLS**，而它是可写角色，不属于"只读调查"可接受的范围 |

由此可以推出一个对迁移设计很关键的事实：

> 平台的 `read` 模式**大概率仍受 RLS 约束**。
> 所以"跨全部 space_id"这件事，即使创建者本人用 `read` 也未必能做到——
> 那需要 `migrate`（有写权限）或者平台侧的数据库备份通道。

这一条必须在收到创建者的实跑结果后确认（看 `count(*)` 是否等于全量）。

## 3. 能否读到六张表的真实总行数

**不能直接读。** 但用你手上已有的两份账号备份，可以得到一个可对照的量：

### 两份备份的 RLS 可见并集（按 `id` 去重）

| 表 | account-A | account-B | 并集 | 你给的期望值 | 差额 |
|---|---|---|---|---|---|
| profiles | 2 | 3 | **3** | 4 | −1 |
| records | 1 | 1 | **1** | 1 | 0 ✓ |
| todos | 3 | 6 | **6** | 9 | −3 |
| tags | 6 | 12 | **12** | 18 | −6 |
| rewards | 0 | 0 | **0** | 0 | 0 ✓ |
| messages | 0 | 0 | **0** | 0 | 0 ✓ |

### 这个差额说明了什么

差额恰好是「1 个成员 + 3 条默认小目标 + 6 条默认标签」——**正好是一个完整空间的最小初始集**。

也就是说：库里存在**第三个空间**，A 和 B 两个账号都不在其中，所以两人都看不见它。

> **更正（2026-10-27，经 Phase 1-c 库内实测确认）**：该空间**不是无成员空间**——完整服务端
> 备份与库内统计显示成员分布为 **2 / 1 / 1**（第三个空间含 1 条 profile），只是该成员不持有
> A、B 任一备份账号。"客户端导出并集 ≠ 数据库总行数"的硬结论不变。

这印证了一条硬结论：

> **客户端导出的并集 ≠ 数据库总行数。** 只要存在"没有任何一个持有账号"的空间，
> 客户端就永远看不到。想拿到 4/1/9/18/0/0 这组数，只能从数据库角色侧查。

A 的可见范围是 1 个空间（2 人），B 是 2 个空间（其中 1 个与 A 共享、1 个只有自己），
两人合计可见 2 个空间，第 3 个空间无人覆盖。

## 4. 能否做只读全量 JSON 导出并存到私有工作区

拆成两问：

| 子问题 | 答案 |
|---|---|
| 能否只读导出 | 能，但**范围 = 当前登录账号的 RLS 可见行**，不是全量。你们已做的 account-A / account-B 就是这个东西。 |
| 能否存到私有工作区 | 能。本地写文件不需要任何额外授权，这两份文件目前就在本机仓库外私有备份目录（路径仅团队内部可知），未上传到任何地方。 |

**"全量"在当前账号下无解**：要全量就得遍历所有空间，而遍历的前提是成为这些空间的成员——
这在逻辑上自相矛盾。

## 5. 需要创建者做什么

按"必须由创建者完成 / 可在你这边完成"分列：

### 必须由创建者完成（3 项）

| # | 事项 | 怎么做 | 为什么只能他做 |
|---|---|---|---|
| A | 导出权威表结构 / RLS / 函数原文 | 在他自己的原工作区，用云数据库工具的 `read` 模式，逐条执行 `backend/schema/999_verify-live-schema.sql` 的 10 段查询，把结果贴回文件末尾 | 只有应用归属账号才能绑定该环境 |
| B | 导出真实总行数 | 同一条 `read` 连接执行 `count(*)`；若因 RLS 被过滤，需改用平台的数据库备份/导出通道（不要用 `migrate` 跑，避免误写） | 同上；且 RLS 可能让 `read` 角色看不到全量 |
| C | 全量数据导出（含第三个空间） | 由他导出 CSV/JSON 全量（他已有 4 张表的 CSV），或走平台备份 | 客户端无法覆盖没有任一备份账号成员的空间 |

### 你这边可以完成（1 项）

| # | 事项 | 说明 |
|---|---|---|
| D | 用两份账号备份做交叉校验 | 已可做：仓库外私有备份目录（路径仅团队内部可知）下有 `compare_backups.py` / `verify_backups.py` / `check_consistency.py`，可以校验"两人看到的重叠部分是否一致"（同一空间、同一条记录，两个账号读到的值必须相同） |

### 如果希望"你也能直接查"——三条现实路径

1. **创建者导副本给你**（最快，零风险，但每次都要他手动）。
2. **把应用迁到团队/组织级空间**：当前平台不支持把云数据库加为协作成员，这条路基本走不通，需向平台确认。
3. **迁出到自建 / Supabase**：那边可以用组织成员 + 只读角色实现真正的协作权限。这是 `docs/08` Phase 2 之后才谈的事。

## 6. 顺手发现的两个事实（影响迁移，不影响线上）

### 6.1 生产 schema 有代码里没出现的字段

从两份备份的字段名看，`profiles` 实际包含 **`target_date`**，而归档的 `index.html`
（2026-10-17 的资料库快照）从不读也不写这个字段。

说明归档的前端副本**不是当前生产构建**，或该字段已废弃但保留。

影响：迁移建表时必须带上它，否则导入会丢数据。已同步修正 `docs/03` 与 `001_tables`。

### 6.2 `created_at` 确认存在，`updated_at` 未见

- `profiles` / `records` / `todos` / `tags` 都有 `created_at`（原推断稿标为"待核对"，现已确认）。
- `records` 的备份行里**没有** `updated_at`（原推断稿里加的字段属于过度设计，已标为可选）。

`rewards` / `messages` 两张表为空，字段仍不可知，等创建者的权威结果补齐。
