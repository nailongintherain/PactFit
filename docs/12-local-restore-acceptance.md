### 3.1 关于数据卷的更正（Step 11 的意外发现）

演练方案最初写的是"不挂载数据卷，容器停止即销毁，零残留"。**这个表述不准确，已更正**：

| 说法 | 准确性 |
|---|---|
| 未显式使用 `-v` / `--mount` | ✅ 事实 |
| 因此不存在数据卷 | ❌ **错误。** `postgres:17` 镜像声明了 `VOLUME /var/lib/postgresql/data`，Docker 会据此**自动创建匿名卷** |
| `--rm` 会清理关联匿名卷 | ⚠️ 部分正确。正常容器移除时通常会清理；但**异常路径（如守护进程重启）下不保证** |
| 容器停了就等于清理完毕 | ❌ **错误。** 必须独立检查容器、匿名卷、临时文件、端口四类残留 |

**实际发生了什么**：演练结束后容器 `pactfit-drill-pg` 已自行消失（守护进程重启导致 auto-remove 容器被清除，容器内残留的 `postmaster.pid` 也印证是非正常终止），但留下 **1 个 dangling 匿名卷**：

| 项 | 值 |
|---|---|
| 卷类型 | 匿名卷（`com.docker.volume.anonymous`），名字为 64 位随机串，**不含项目前缀** |
| 体积 | 48.67 MB |
| 创建时间 | 与演练容器创建同一时刻 |
| 内容判定 | 只读挂载到 `/inspect` 后，仅检查目录结构与 `PG_VERSION`，得 **`17`** 且为标准 PG 数据目录（`base/` `global/` `pg_wal/` `postgresql.conf` 等）→ 确认为演练库数据目录 |

**为什么这条坑值得记**：用 `docker volume ls | grep pactfit` 查匿名卷**永远查不到**（名字里没有项目名），会得出"无残留数据卷"的假结论。正确查法是 `docker volume ls --filter dangling=true`。

**清理做法**（Step 11 已执行，PASS）：

1. 归属核验：一次性容器 + `--mount source=<卷ID>,target=/inspect,readonly`，
   并用 `--tmpfs /var/lib/postgresql/data` **覆盖镜像默认 `VOLUME` 路径**，避免检查容器自己再造一个匿名卷；
   `--network none`、`--entrypoint sh`（不启动 PostgreSQL），只读目录名与 `PG_VERSION`，不读任何表文件；
2. 定向删除：`docker volume rm <完整卷 ID>`（**不使用任何 prune**）；
3. 独立复核：容器 0、卷 0、临时目录不存在、端口无监听、原始备份 `SHA256SUMS` **12/12 OK**。

## 6. 原始主键与 identity 序列验证

### 6.1 为什么要单独验

- `GENERATED ALWAYS AS IDENTITY` 的列导入时必须 `OVERRIDING SYSTEM VALUE`，否则报错；
- 导入**不会**自动推进序列，序列若停在 1，下一条真实插入会撞主键；
- `nextval` **不是事务性的**，回滚不会退回号，因此任何"试号"都会真实消耗序列。

### 6.2 主键保真

| 表 | `max(id)` | 说明 |
|---|---|---|
| `profiles` | **22** | 4 行，主键不连续 |
| `records` | **6** | 1 行 |
| `todos` | **14** | 9 行 |
| `tags` | **24** | 18 行 |

主键明显**不是 1..N**，说明原始主键被完整保留、没有重编号 —— 这是"保真"的关键证据，
因为 `records.todo_done` 里存的是 todo 的 id 数组，一旦重编号，引用关系就全断了。

### 6.3 序列修正

| 表 | `last_value` | `is_called` | 结论 |
|---|---|---|---|
| `profiles` | 22 | true | = `max(id)` ✅ |
| `records` | 6 | true | = `max(id)` ✅ |
| `todos` | 14 | true | = `max(id)` ✅ |
| `tags` | 24 | true | = `max(id)` ✅ |
| `rewards` | 1 | false | 空表，从 1 开始且未取号 ✅ |
| `messages` | 1 | false | 空表，从 1 开始且未取号 ✅ |

**撞号探针实测**：插入一条临时 todo，取得 id = **15**（= 14 + 1，符合"先取号再插入"），
随后删除该行并把序列**显式写回 14**；末尾四项核实行 `seq = 14 / max_id = 14 / rows = 9 / probe_left = 0`。
即：探针验证了"下一条会拿到 15"，同时**序列已复原**，后续真实插入不会跳到 15 之后。

> 一个容易误判的口径：`pg_sequences` 视图对 `is_called = false` 的序列返回 `last_value = NULL`，
> 看起来像"序列没初始化"。权威读法是直接 `select last_value, is_called from <序列>`。
> 本报告中 rewards / messages 的 `1 / false` 即由此读法所得。

| **合计** | **240** | **0** | **0** | — |

退出码 **0**，结论 **PASS**。

### 8.3 三态判定规则

每格只可能是三种结论，**"量化"必须被显式打印出来**，不能混进"一致"里：

| 类型 | 一致 | 已量化（单独计数） | 差异 |
|---|---|---|---|
| `numeric(5,1)` | 数值完全相等 | 源值小数位超 1 位，四舍五入后相等 | 量化后仍不等 |
| `date` | 日期相同 | 源里带时分秒，落库只剩日期 | 日期不同 |
| `timestamptz` | 时刻完全相同 | 小数秒超 6 位，按 PG 规则**四舍五入**到微秒后相同 | 时刻不同（含 1µs 真偏差） |
| `jsonb` | 语义相等（键序/空格无关） | — | 语义不同 |
| 其他 | 逐字符相等 | — | 不同 |
| NULL | 两侧同为 NULL | — | 一侧有值一侧 NULL |

> `timestamptz` 不能"先转 `datetime` 再比"：Python 的 `datetime` 只有微秒，
> `fromisoformat` 对 `.123456789` 是**截断**，而 PostgreSQL 是**四舍五入**（→ `.123457`）。
> 拿截断值去比会把正常量化误报成真实差异，所以脚本用精确十进制保留原始小数位，
> 再按 `HALF_UP` 量化到 6 位比较。

### 8.4 严格精度复核

追加 `--strict-precision`（口径：**量化也必须为 0，一位小数都不能变**）后**同判 PASS**。
这比默认口径更严，说明连"被量化掩盖的偏差"也不存在 —— 240 次取值是**逐位相同**，不是"量化后相同"。

### 8.5 临时文件处置

`--purge-on-pass` 在判 PASS 后自动删除导出文件。当前 `~/PactFit-drill/` 仅剩
`20_import.sql`（8,155 B，0600）与 `expected.json`（3,160 B，0600），目录 0700。

## 9. RLS 权限隔离测试（18 项）

### 9.1 设计要点

| 要点 | 做法 |
|---|---|
| 身份切换 | **psql 层** session 级 `SET ROLE authenticated` / `RESET ROLE`。**不在 PL/pgSQL 里切角色** —— `SET LOCAL` 的作用域是当前事务/子事务，异常回滚会把角色设置一起丢掉 |
| 记账两段式 | 阶段 C（`postgres`）算预期并保存基线 → 阶段 D（`authenticated`）只查询与探针 → 阶段 E（`postgres`）判定 |
| 未授权空间选取 | `space_id NOT IN (该用户的全部空间)`；选不出则判 `INCONCLUSIVE`，**整轮按不通过处理** |
| 探针回滚 | 三段探针（跨空间 `INSERT`、同空间 `INSERT`、跨空间 `UPDATE`）**全部包显式事务并无条件 `ROLLBACK`**，不依赖"被拒绝所以语句自身回滚"这种间接保证 |
| 失败侧默认值 | `xs_ok` / `ss_ok` / `up_ok` 预置为"失败侧"，语句没执行也不会被当成成功 |
| 探针标记 | `drill-rls-probe-` + 微秒时间戳 + pid + 随机串，唯一且可追溯 |
| 不兜底删除 | 残留只**计数断言**，不 `DELETE`。残留就是回滚链路失效的信号，删掉只会掩盖异常 |
| 判定标准 | 跨空间写入必须 `SQLSTATE = 42501` **且** 消息含 `row-level security`；同为 42501 的 `permission denied for schema` 一律 FAIL |

### 9.2 18 项结果（全部 PASS，退出码 0）

| # | 检查项 | 实测 |
|---|---|---|
| 1 | 执行身份 | `current_user = authenticated` ✅ |
| 2 | `auth.uid()` 等于测试身份 | `true` ✅ |
| 3 | 可见空间数 | 与该用户全部空间数一致 ✅ |
| 4 | `my_space_ids()` 空间数 | 一致 ✅ |
| 5 | `profiles` 可见行数 | 一致 ✅ |
| 6 | `records` 可见行数 | 一致 ✅ |
| 7 | `todos` 可见行数 | 一致 ✅ |
| 8 | `tags` 可见行数 | 一致 ✅ |
| 9 | `messages` 可见行数 | 一致（空表） ✅ |
| 10 | 未授权空间可见行数 | **0** ✅ |
| 11 | 跨空间写入 | `sqlstate = 42501`，**消息含 row-level security = true** ✅ |
| 12 | 同空间写入 | `returning id` 拿到正数 id（确认真写入），随后 `ROLLBACK` ✅ |

### 9.3 第 11 项为什么必须双重判定

`permission denied for schema auth` 与"RLS 拒绝写入"**同为 SQLSTATE 42501**。
如果只判错误码，一个"因为没给 schema USAGE 而写不进去"的假象会被当成"隔离生效"，得出**假 PASS**。

因此：
- 演练 harness 先补 `grant usage on schema auth`（自检第 4 列 `t` 即为此项）；
- 判定时同时要求**消息含 `row-level security`**，且只打印 `true/false`、不打印错误原文。

### 为什么不在演练里顺手修掉

1. **演练的目的是验证还原保真度**，不是修数据。任何"顺手修一下"都会让"备份 = 恢复库"的等式失效，比对结果就失去意义。
2. **修数据需要产品决策**：这条引用应该补一条 todo、还是从数组里摘掉？摘掉会改变用户的打卡历史语义，属业务决定，不是工程决定。
3. **迁移时同样要原样带过去**，否则新旧系统对同一段历史会给出不同解释。

> 建议：在 Phase 1-d 数据迁移前，单独开一张"历史数据瑕疵"工单，明确这三件事 ——
> 修不修、谁来定、修了怎么记录版本。**不要混进迁移动作里。**

## 14. 结论边界声明（必读）

1. **18 项 RLS PASS ≠ 完整安全审计。**
   这 18 项只回答一个问题：*"旧策略在旧数据上，能不能拦住跨空间的读写改？"*
   它**没有**检查权限设计的合理性、没有做越权路径枚举、没有做注入与提权测试、
   没有验证生产授权矩阵冗余项（明细仅存私有归档）的真实危害。通过它只说明"策略确实生效了"，
   不说明"策略是对的"。

2. **旧权限策略不得原样迁移到 Supabase。**
   演练**刻意复现**了旧策略（包括 §11.1 列出的缺陷），目的是观察而非背书。
   直接照搬会把 S1–S3 一起搬进新系统，且新系统的 `auth.uid()` 返回 `uuid`，
   所有策略表达式都必须重写 —— 这本来就是一次重新设计的机会，不该浪费在"复制粘贴"上。

3. **恢复演练通过 ≠ 迁移就绪。**
   本次只证明了"数据能从备份还原到 PostgreSQL 17.11"，且"还原后逐字段一致"。
   认证、目标环境、前端、切换方案**一处都没动**。

4. **本报告不构成对生产数据质量的认可。**
   §10 的悬空引用是既存问题；是否还有其它数据瑕疵，本次只覆盖了
   `reconciliation.json` 已记录的两类（悬空引用、账号无档案）。

5. **所有结论仅对 `postgres:17` / 17.11 成立。**
   跨大版本（16 / 18）的行为差异未验证，不能外推。
